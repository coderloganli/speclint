# General software glossary for speclint.
#
# Technical terms and names that are correct in software documents. A word
# that is not in the word list passes the vocabulary check if it is in this
# glossary or in the project glossary (.speclint/glossary.txt). One entry on
# each line:
#
#   term | pos | category | note
#
# term:     the base form; it can have more than one word ("pull request")
# pos:      n (noun) or v (verb)
# category: why the term is necessary:
#   name       products, programming languages, standards, organizations (n)
#   component  systems, software components, configurations, infrastructure (n)
#   concept    engineering, mathematics, and computing concepts; data types (n)
#   device     machines and computers (n)
#   unit       units of measurement, time, and dates (n)
#   document   documents and parts of documents, such as section, table,
#              figure, and step; a word that is only a heading, such as goal
#              or scope, is not a part of a document (n)
#   role       persons and groups (n)
#   operation  computer operations (v); use one only if no common verb gives
#              the same information
# note:     optional
#
# Well-known products, programming languages, and open standards are in this
# glossary. The names of the project itself and its domain words (such as
# "invoice") go in the project glossary.
#
# A lowercase term matches with any case. A term with an uppercase letter
# (a name, such as "GitHub") matches only with the same case.
#
# Use one term for one item, and no slang: "repository", not "repo";
# "configuration", not "config"; "PostgreSQL", not "Postgres".
